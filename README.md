# CreditAssessmentMemo - Automated CAM Generation for Indian SME Lending

An end-to-end pipeline that ingests a company's financial documents and generates a structured, 10-section **Credit Assessment Memo (CAM)** as a Word document. Built during a GenAI internship.

The pipeline combines **RAG over unstructured documents** (ChromaDB), **structured financial data** (MySQL), **keyword-based reconciliation** across sources, and a **LangGraph workflow** that generates sections in parallel and runs them through a deterministic quality gate before the final document is written.

---

## Features

- **Five document types ingested:** annual reports, audit reports, exchange filings (board meeting and shareholder meeting outcomes), bank statements, and Screener.in Excel exports.
- **Per-section retrieval:** each CAM section runs its own ChromaDB queries, with standalone-only filtering for financial sections.
- **Verified-facts context:** figures from MySQL are injected into every section prompt to prevent unit errors and cross-section contradictions.
- **Keyword reconciliation:** database values are checked against document evidence in pure Python, with no LLM involved.
- **Parallel generation:** the 10 sections are generated concurrently using LangGraph's `Send` API, with a configurable concurrency cap.
- **Deterministic review loop:** each section is checked for known defect classes, and only failed sections are regenerated with targeted feedback.
- **Run report:** every run writes a JSON audit trail alongside the `.docx`.
- **Resume-on-failure ingestion:** progress is tracked per document type, so a crashed run skips completed steps when restarted.
- **Provider-agnostic LLM layer:** switch between Gemini, OpenAI and Azure OpenAI with a single environment variable.

## Architecture

### Ingestion (`parser_agent.py`)

```
Input folder
 ├─ annual_report/     → pdfplumber parsing, page classification → ChromaDB
 ├─ audit_report/      → same pipeline as annual report           → ChromaDB
 ├─ saverisk/          → pandas + LLM label resolution            → MySQL
 ├─ exchange_filings/  → pdfplumber + Gemini vision OCR fallback  → ChromaDB
 └─ bank_statements/   → RAG chunks + LLM summary                 → ChromaDB + MySQL
```

### CAM Generation (`cam_langgraphh.py`)

```
START → ingest → load_data ──(company not found)──→ END
                     ↓
                 retrieve → reconcile
                              ↓  (fan-out: one task per section)
                       generate_section ×10
                              ↓
                           review ──(failed, retries left)──→ generate_section (failed only)
                              ↓
                            write → END
```

| Node | Responsibility |
|---|---|
| `ingest` | Runs the parser agent; skips steps already completed |
| `load_data` | Loads the company bundle from MySQL and builds the verified-facts context |
| `retrieve` | Per-section ChromaDB retrieval using `schema.SECTION_QUERIES` |
| `reconcile` | Keyword-based check of database values against evidence |
| `generate_section` | Generates one section; runs in parallel, failures are contained |
| `review` | Deterministic checks; routes failed sections back with feedback |
| `write` | Writes the `.docx` and the JSON run report |

### Review checks

The review node is plain Python, not an LLM. It flags:

- Empty or very short sections.
- Figures expressed in US dollars in an INR memo.
- Claims that information is missing when several evidence blocks were supplied.
- Missing or invalid structured tables in table sections.
- An unconditional recommendation when reconciliation shows unverified fields.

## Setup

### 1. Install dependencies

```bash
pip install langgraph google-genai openai chromadb mysql-connector-python \
            pdfplumber pymupdf==1.23.8 pandas openpyxl python-docx python-dotenv
```

> `pymupdf` is pinned to 1.23.8 because newer builds can be blocked by Windows Application Control policies.

### 2. Configure `.env`

```env
# LLM
GEMINI_API_KEY=your_key
GEMINI_MODEL=gemini-2.5-flash
LLM_PROVIDER=gemini            # gemini | openai | azure_openai

# Optional providers
OPENAI_API_KEY=
AZURE_OPENAI_API_KEY=
AZURE_OPENAI_ENDPOINT=
AZURE_OPENAI_DEPLOYMENT=

# MySQL
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASSWORD=your_password
DB_NAME=credit_memo

# Graph settings
CAM_MAX_PARALLEL_SECTIONS=3    # keep low on free-tier Gemini
CAM_MAX_REVIEW_RETRIES=1

# Optional tracing
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=
```

### 3. Initialise the database

```bash
python db.py
```

## Usage

### 1. Prepare the input folder

```
Inputs/<Company Name>/
 ├─ annual_report/      one .pdf
 ├─ audit_report/       one .pdf
 ├─ saverisk/           one .xlsx or .xls (Screener.in export)
 ├─ exchange_filings/   one or more .pdf
 └─ bank_statements/    one or more .pdf / .xlsx / .xls / .csv
```

### 2. Run the pipeline

Set the company in the `__main__` block of `cam_langgraphh.py`, then:

```bash
python cam_langgraphh.py
```

Or from Python:

```python
from cam_langgraphh import run_cam

run_cam(
    company_name="Durlax Top Surface Limited",
    fiscal_year=2025,
    folder_path=r"Inputs\Durlax Top Surface Limited",
)
```

### 3. Outputs

| File | Contents |
|---|---|
| `<Company>_CAM.docx` | The 10-section Credit Assessment Memo |
| `<Company>_CAM_run_report.json` | Node timings, chunks per section, reconciliation counts, review retries, unresolved issues, errors |

### Reset all data

```bash
python test_reset.py
```

This wipes every MySQL table, including ingestion progress, and every ChromaDB chunk.

### View the graph

```python
from cam_langgraphh import export_graph_diagram
export_graph_diagram()   # writes cam_graph.mmd; paste into mermaid.live
```

## Key Design Decisions

- **RAG plus structured data.** CAM writing is open-ended, so unstructured documents go to ChromaDB. Fields that need deterministic checks go to MySQL.
- **Keyword-only reconciliation.** Regex-based numeric comparison produced false mismatches across multi-column financial tables, so status is based on keyword presence and the LLM verifies numbers from the raw evidence.
- **Deterministic review over LLM review.** Most defects traced during development came from wiring and data issues rather than hallucination, so the quality gate encodes those failure modes directly in code.
- **Standalone-only financial sections.** Consolidated group figures are filtered out of Financial Analysis, Risk Assessment and Recommendation to avoid inflated or contradictory numbers.
- **No hardcoded figures.** Units, currency and company facts are always derived from MySQL.

---

## Limitations

- Reconciliation confirms that evidence exists for a field; it does not compare numbers.
- Two-column layout detection uses a fixed 50% page split and may misclassify pages with unequal column widths.
- Borrower-provided documents (GST returns, ITRs, sanction letters, credit rating reports, valuation reports) are out of scope.
- Bank statements used for testing are synthetic and clearly watermarked.
